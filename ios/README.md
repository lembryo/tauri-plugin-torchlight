# tauri-plugin-torchlight (iOS)

The iOS half of [`tauri-plugin-torchlight`](../README.md). It controls the device
torch through `AVFoundation`'s `AVCaptureDevice` and is loaded automatically by
the plugin's Rust `mobile` bridge — you normally do not interact with this
package directly.

## What it does

Commands exposed to the Rust bridge:

- `torch` — turns the torch on/off. When turning on, an optional `level`
  (`0.0...1.0`) sets the brightness; a level that is effectively maximum uses
  `AVCaptureMaxAvailableTorchLevel` to avoid the throw that passing `1.0`
  directly can cause.
- `toggle` — flips the torch inside the native plugin and resolves with the
  resulting `enabled` state, so two concurrent toggles cannot both observe the
  same starting state. An optional `level` is applied only when the flip turns
  the torch on.
- `isAvailable` — reports whether the default video device has a torch
  (static hardware presence).
- `isEnabled` — reports whether the torch is currently active.
- `capabilities` — reports `available`, `usable` (`isTorchAvailable`, i.e.
  whether the torch works right now), `brightnessSupported` (always `true` on
  iOS, which exposes a continuous `0...1` level) and `levelSteps` (always
  `null`, because the scale is continuous rather than discrete).
- `torchModeChanged` event — emitted via KVO so the WebView stays in sync when
  the system changes torch state (other capture sessions, thermal limits, etc.).

### Brightness math (`TorchMath`)

`TorchMath.clampLevel(_:)` normalizes the optional level before it reaches
`setTorchModeOn(level:)`:

- `nil` and non-finite values (`NaN`, `±Infinity`) mean "no explicit level
  requested" and map to **full brightness**.
- Finite values are clamped into `TorchMath.minLevel...1.0`.

`TorchMath.minLevel` is `0.01`, and the floor is not cosmetic:
`AVCaptureDevice.setTorchModeOn(level: 0.0)` raises an **Objective-C
`NSInvalidArgumentException`**, which Swift's `do`/`catch` cannot catch, so it
would terminate the process. Zero is therefore floored rather than passed
through — which also matches Android, where a requested `0.0` maps onto the
minimum "on" strength. The shared contract is that `0` means "as dim as
possible", never "off".

### Concurrency and locking

A serial `DispatchQueue` (`com.lembryo.tauri.plugin.torchlight`) serializes
every configuration change, so concurrent invocations cannot unbalance each
other's `lockForConfiguration()`. Inside it, the device is always reconfigured
between `lockForConfiguration()` / `unlockForConfiguration()`, with the unlock
guaranteed by a `defer` so the device is never left locked if a torch call
throws.

### Observation

KVO observes **both** `isTorchActive` and `isTorchAvailable`. Availability is
observed separately because it can change while the torch is off, which
`isTorchActive` alone would never report. No event is emitted at `load()`: it runs before the WebView can register a
listener, and Tauri's `trigger` drops a payload when none exists. Read the initial
state with `isEnabled` / `capabilities` instead; the event covers changes only.

### Errors

Rejections carry a machine-readable `code` alongside the message, which the
Rust side surfaces as `TorchlightError.kind`:

- `unavailable` — the default video device has no torch.
- `torchFailed` — the torch could not be driven (e.g.
  `AVErrorTorchLevelUnavailable` under thermal pressure).

## Requirements

- iOS 13+ (see [`Package.swift`](Package.swift)).

## Tests

`Tests/PluginTests` contains host-runnable unit tests for the pure brightness
math (`TorchMath`), which is deliberately kept free of AVFoundation/UIKit so it
can be tested without a device or simulator.

`Package.swift` depends on the `Tauri` package at `../.tauri/tauri-api`, so
`ios/.tauri/tauri-api` must exist before `swift test` can resolve the package.
That scaffolding is generated by the Tauri CLI for a host app's iOS project —
for example the driver app that consumes this plugin — not by this repository.
Once it is in place, run the tests from an iOS toolchain (Xcode or `swift test`
on macOS).
