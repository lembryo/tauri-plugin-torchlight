# tauri-plugin-torchlight

Tauri v2 plugin that drives the smartphone torch on Android and iOS. Published as
two packages that are released together and share one version number:
`tauri-plugin-torchlight` (crates.io) and `tauri-plugin-torchlight-api` (npm).

## Layout

| Path | What lives there |
| --- | --- |
| `src/` | Rust: plugin entry, commands, wire models, error type, desktop stub, mobile bridge |
| `guest-js/index.ts` | The TypeScript bindings — the API consumers actually use |
| `android/src/main/java/` | Kotlin plugin (`TorchlightPlugin.kt`) + pure math (`TorchMath.kt`) |
| `ios/Sources/` | Swift plugin (`TorchlightPlugin.swift`) + pure math (`TorchMath.swift`) |
| `permissions/` | ACL. `default.toml` is hand-written; everything under `autogenerated/` is not |
| `docs/` | Hand-written GitHub Pages site (ja + en), excluded from the crate |

## Architecture

`src/lib.rs` registers the commands and picks an implementation by target:
`desktop.rs` is a stub that returns `Error::Unsupported` for mutations and `false`
for queries; `mobile.rs` forwards to the native plugin over `run_mobile_plugin`.
`TorchlightExt` is how Rust callers reach it (`app.torchlight()`).

Commands: `torch`, `toggle`, `is_available`, `is_enabled`, `capabilities`, plus
`register_listener` / `remove_listener`. The listener pair is **not** implemented
by us on mobile — Tauri's mobile runtime handles it so `addPluginListener` works.
On desktop there is no such runtime, so `commands::desktop_listeners` registers
no-op stand-ins; without them `onTorchModeChanged` would reject with "command not
found" and every consumer would need to special-case the platform.

The event `torchModeChanged` carries `{ enabled, available }`.

## Invariants — break these and things fail quietly

- **`build.rs`'s `COMMANDS` list is the source of the ACL.** Adding a command means
  adding it there, running `cargo build` to regenerate `permissions/autogenerated/`,
  and adding the `allow-*` entry to `permissions/default.toml` by hand.
- **Command names are snake_case on the wire.** `@tauri-apps/api` invokes
  `plugin:torchlight|register_listener` first and only falls back to camelCase for
  backwards compatibility. Tauri does no case normalisation on the ACL path.
- **`level` semantics are shared across platforms.** `0` means "as dim as this
  device allows", never "off". iOS floors at `TorchMath.minLevel` (0.01) because
  `setTorchModeOn(level: 0.0)` raises an Objective-C `NSInvalidArgumentException`,
  which Swift `do`/`catch` cannot catch — it terminates the process. Rust's
  `sanitize_level` clamps and drops non-finite values before they reach a native.
- **`available` is two different predicates.** `isAvailable()` and
  `TorchCapabilities.available` mean *hardware exists* and never change.
  `TorchCapabilities.usable` and the event's `available` mean *works right now*.
  Do not collapse them.
- **Android's `TorchCallback` must be unregistered.** It registers into a
  process-scoped singleton that holds the plugin and therefore the Activity;
  `onDestroy` unregisters it. Registering twice emits duplicate events.
- **Android's cached `torchEnabled` is updated optimistically** in `applyTorch`
  before resolving, because the callback arrives asynchronously on the main looper.
  Without that, `isEnabled()` lies immediately after a successful `torch()`.
- **Error codes are a three-way contract.** The Kotlin/Swift `reject(message, code)`
  codes, Rust's `Error::kind()`, and the TypeScript `TorchErrorKind` union must stay
  in sync. The union is `unsupported | unavailable | cameraAccess | torchFailed |
  internal`, but no single layer emits all five — nothing enforces this, so keep the
  three lists aligned by hand:
  - Kotlin `ErrorCode` emits `unavailable`, `cameraAccess`, `torchFailed`.
  - Swift `ErrorCode` emits only `unavailable` and `torchFailed` (there is no
    `cameraAccess` on iOS).
  - Rust adds `unsupported` (desktop only) and falls back to `torchFailed` for a
    rejection with no code, `internal` for any other `PluginInvokeError`.
- **`dist-js/` is gitignored and built by rollup.** Consumers using a `file:`
  dependency get a symlink, not a build — the driver app runs `build:plugin` in its
  `predev`/`prebuild` for exactly this reason.
- **`package-lock.json` is committed, `Cargo.lock` is not.** The publish workflow
  runs a plain `npm ci`, which needs the lockfile; `Cargo.lock` is gitignored
  because a library leaves dependency resolution to its consumers.

## Commands

```bash
cargo test                  # Rust unit tests (desktop target)
cargo clippy --all-targets -- -D warnings
npm run build               # rollup -> dist-js/
npm run typecheck           # tsc --noEmit
npm test                    # pretest builds, then tsc --noEmit
```

Android unit tests need a Gradle wrapper and the CLI-generated `.tauri/tauri-api`,
neither of which is committed in this repo (`android/.gitignore` ignores `/gradle`
and `/.tauri`; there is no `android/gradlew` at all). Run them from the driver app's
generated project instead:
`cd src-tauri/gen/android && ./gradlew :tauri-plugin-torchlight:test`.

iOS tests need `ios/.tauri/tauri-api`, also CLI-generated, and a macOS host.

## Releasing

`.github/workflows/publish.yml` runs on push to `main`: a `Test` gate (a guard that
`Cargo.toml` and `package.json` versions agree, `cargo clippy --all-targets -- -D
warnings`, `cargo test`, `npm ci`, `npm run build`), then `Publish to npm`, then
`Publish to crates.io` — each `needs` the previous one. npm goes first because it is the reversible half
— a crates.io publish cannot be undone. Already-published versions are skipped, so
merging without a version bump is a no-op.

**Bump `Cargo.toml` and `package.json` together.** The version guard fails the
build if they diverge.
